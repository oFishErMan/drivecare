### 문제와 우선순위

- 기존: 교체 기록은 저장되지만 소모품별 카드에서 따로 확인해야 한다. 관리 종료된 항목의 기록도 DB에는 남지만 카드에서 찾을 수 없다.
- 가설: 차량 관리에서 최신 교체 기록을 바로 열고 파일을 받을 수 있으면, 과거 정비 확인·백업을 위해 여러 화면을 오갈 필요가 줄어든다.
- 이번 선택: 차량 단위 이력 조회와 CSV. 기존 기록을 활용해 스키마 변경 없이 제공할 수 있다.
- 다음 후보: (1) 거리 입력이 오래된 차량에 갱신 안내를 제공해 알림 판단 근거를 보여주기 (2) 실제 사용에서 이력이 길어지면 기간 필터와 내보내기 범위 추가 (3) 수요 확인 후 정비 영수증 첨부 검토. 알림 채널 확대, 외부 데이터 연동은 보안·운영 비용 때문에 보류한다.

### 수용 기준

1. 차량 관리에서 선택 차량의 교체 기록을 날짜 내림차순으로 조회한다. 같은 날짜는 기록 ID 내림차순으로 정렬하고, 20건씩 표시한다.
2. 관리 종료한 소모품은 과거 기록을 유지하되 현재 상태를 명시한다. 구매 URL·이메일·다른 차량의 이력은 결과에 넣지 않는다.
3. 본인 차량에만 조회·다운로드를 허용한다. 미인증은 401, 다른 계정과 존재하지 않는 차량은 404로 응답한다.
4. CSV는 UTF-8 BOM을 사용한다. 제품명의 쉼표·따옴표는 이스케이프하고 수식처럼 시작하는 값은 CSV 출력에서만 텍스트 표식을 붙인다. [OWASP CSV Injection](https://owasp.org/www-community/attacks/CSV_Injection) 참고. 원본 DB 값은 바꾸지 않는다.
5. 파일은 요청 시 생성하며 서버에 보관하지 않는다. 5,000건을 넘기면 422로 안내하고 파일을 조용히 잘라 제공하지 않는다. 파일은 자체 입력한 기록이며 공식 정비 증명서가 아니다.

- 이후 사용자 검증: 첫 방문과 재방문 각각에서 과거 교체일을 찾아 CSV를 받는 과제를 관찰한다. 소요 시간·화면 이동 횟수·혼동한 문구를 기록한다. 이번 사이클에서 사용성 개선 수치를 측정했다고 주장하지 않는다.

### 범위 및 운영

- 읽기 API: `GET /api/vehicles/{id}/history?page=0`, `GET /api/vehicles/{id}/history/export`. 페이지 번호는 0부터 시작한다.
- 조회와 내보내기 모두 차량과 소유자 조건을 함께 사용한다. 목록은 offset 기반이며, 페이지 이동 중 새 기록이 저장되면 행 위치가 달라질 수 있다.
- 5,000건 상한은 단일 요청 메모리를 제한하기 위한 값이다. 대규모 데이터 이전과 포맷 재가져오기는 보장하지 않는다.
- 배포 순서: 백엔드 먼저, 프런트엔드 다음. 기존 API·스키마 변경 없음. 서비스 컨테이너만 이전 이미지로 되돌릴 수 있다.

### 로컬 릴리스 기록

- 앱 컨테이너 두 개만 교체했다. MariaDB·Redis 컨테이너 ID는 이전과 동일했다.
- 로컬 배포에서 새 UI 번들과 OpenAPI의 이력 경로 2개, 미인증 요청의 401을 확인했다. 이력의 정상 데이터와 소유권은 MockMvc·격리된 MariaDB 테스트에서 검증했다.
