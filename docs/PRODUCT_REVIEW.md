# DriveCare 화면 전수 검토 및 개선 기획서

작성일: 2026-10-15 · 검토 역할: 서비스 기획자 · 대상: 현재 구현된 웹 서비스

## 목적과 판단 기준

운전자가 접속 후 “어느 차량의 무엇을 먼저 교체해야 하는가”를 이해하고, 주행거리 갱신·교체 기록까지
이어갈 수 있도록 한다. 기능의 존재뿐 아니라 발견 가능성, 정보의 근거, 오류 회복, 모바일 조작을 검토한다.
이번 작업은 기획 → 디자인 명세 전달 → 개발 → 검수 순으로 수행하며, 실제 외부 사람에게 발송하지 않고
프로젝트 문서로 인계한다. 구현 범위는 아래 확정 요구사항이다.

## 조사 범위와 방법

| 영역 | 검토한 화면/상태 | 근거 |
| --- | --- | --- |
| 공통 | 로그인 복원, 초기 로딩/실패, 헤더, 탭, 해시, 키보드, 뒤로 가기, 스크롤바 | 실행 화면 + 소스 |
| 정비 현황 | 정상/임박/초과/기간 전용, 교체 기록, 이력, 링크 관리, 삭제 확인 | 실행 화면 + DTO/소스 |
| 차량 관리 | 등록 폼 접기, 주행거리 갱신, 다차량 식별, 등록 후 이동 | 실행 화면 + 소스 |
| 소모품 등록 | 차량·종류 선택, 필수/선택, 교체 기록, 거리/기간 주기, 구매 링크 | 실행 화면 + 소스 |
| 알림 | 읽음/미확인, 지난 알림과 현재 상태, 브라우저 권한 안내 | 실행 화면 + 소스 |
| 인증 | 로그인/가입, 비밀번호 표시, 입력 검증, 실패/처리 중 | 소스 검토; 최종 실행 검수는 별도 기록 |
| 빈 화면/실패 | 차량 없음, 소모품 없음, 검색 결과 없음, 네트워크 오류, 변경 충돌 | 소스 + 로컬 검증 시나리오 |

사용자 인터뷰나 사용성 실험을 수행한 것은 아니다. 아래 문제는 화면 관찰과 코드에 근거한 기획 판단이며,
성능·접근성 인증이나 실제 이용률 개선을 보장하지 않는다.

## 사용자 흐름

신규: 계정 생성 → 로그인 → 차량 등록 → 해당 차량 소모품 등록 → 정비 현황.
재방문: 정비 현황의 우선순위 확인 → 필요하면 주행거리 갱신 → 교체 기록 저장 → 재계산 결과 확인.
알림: 미확인 알림 확인 → 해당 소모품의 현재 상태 보기 → 정비 후 기록.

등록을 탭으로 분리한 구조, 입력 중 탭 이동 보존, 스크롤바 공간 고정은 유지한다.
주행거리 추정일은 참고값이며 제조사 권장 정비일이나 실시간 운행 데이터라고 표현하지 않는다.
기존 구매 링크는 사용자가 저장한 주소이며 제휴/가격 비교/매출 발생으로 표현하지 않는다.

## 이후 별도 정책이 필요한 항목

- 차량 수정·매각/삭제, 교체 이력 정정/복구: 데이터 관계와 정정 이력 정책 설계 후 개발.
- 비밀번호 재설정·회원 탈퇴: 메일 발송과 데이터 삭제 범위 결정 후 개발.
- 페이지 종료 후 Web Push: 서비스 워커·구독 해제·HTTPS·재시도 정책 설계 후 개발.
- 모든 알림 일괄 읽음: 서버의 일괄 처리 계약을 추가할 때 검토.

위 항목은 이번 화면 개선의 완료 항목으로 표시하지 않는다.
